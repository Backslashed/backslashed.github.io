A static site generator in Swift

5 September 2026

This site is generated by a small program written in Swift. That is not a remarkable choice on its own — everyone has written a static site generator — but two decisions made it more interesting than the usual weekend exercise.

The first: the output ships no JavaScript. Not “minimal”, not “only for analytics”. None. The second follows from it — if you want syntax-highlighted code and no client-side highlighter, you have to tokenize at build time, and then you have to decide what does the tokenizing.

Markdown can’t say everything#

Plain Markdown has no way to caption an image, group a set of screenshots, or attach metadata to a page. The usual answers are Hugo-style shortcodes ({{< image >}}), which require munging the text before it reaches the parser, or stuffing everything into front matter, which drags layout decisions out of the document.

There’s a third option that Swift developers already have sitting in front of them. swift-markdown supports block directives — the @Something(...) syntax DocC uses — and they’re handled by the real parser rather than a pre-pass:

let document = Document(parsing: source, options: [.parseBlockDirectives])

That flag is the entire trick, and forgetting it is the first bug you’ll write: without it, @Gallery(columns: 4) parses as an ordinary paragraph and silently renders as literal text on your page. With it, you get a BlockDirective node carrying a name, parsed name: value arguments, and block children:

mutating func visitBlockDirective(_ directive: BlockDirective) {
    let arguments = directive.argumentText.parseNameValueArguments()
    switch directive.name {
    case "Gallery":
        let columns = arguments.first { $0.name == "columns" }
            .flatMap { Int($0.value) } ?? 3
        renderGallery(in: directive, columns: columns)
    default:
        fail("unknown directive `@\(directive.name)`")
    }
}

Note

That default case matters more than it looks. An unknown directive is a build error here, not a no-op — otherwise a typo like @Galery vanishes from the page and you find out months later.

So ordinary ![alt](image.png) still works and gets thumbnailed like anything else, and the directives exist only for what Markdown genuinely cannot express.

Highlighting Swift with the Swift parser#

The obvious library for build-time Swift highlighting is Splash. I nearly used it, then checked: its last commit is from June 2022, and it contains exactly one grammar file. It predates macros, typed throws, parameter packs and ~Copyable — which is to say it predates most of what I’d want to write a blog post about.

The alternative is to use the compiler’s own parser. swift-syntax ships SwiftIDEUtils, which exists for precisely this:

let tree = Parser.parse(source: code)
for classified in tree.classifications {
    switch classified.kind {
    case .keyword:       emit("hl-keyword", classified.range)
    case .type:          emit("hl-type", classified.range)
    case .stringLiteral: emit("hl-string", classified.range)
    default:             emitPlain(classified.range)
    }
}

The worry with this approach is fragments. A Markdown code block is rarely a valid source file — it’s three statements, or a method with an unbalanced brace, or something with // ... standing in for the boring part. A parser that rejects those would be useless here.

It doesn’t reject them. Parser.parse(source:) is non-throwing and non-optional: it always returns a tree, using error recovery to insert missing and unexpected nodes where the source doesn’t parse. Since highlighting only reads classifications and ignores diagnostics entirely, a broken fragment degrades to slightly plainer text and the build carries on.

The cost is honest: swift-syntax is a large dependency and a clean build takes a few minutes. In exchange, the highlighting is done by the same parser Xcode uses, and it will never fall behind the language.

What no JavaScript actually forces#

Removing JavaScript is easy to say and mostly easy to do, but it does make specific decisions for you:

  • Galleries are a CSS grid of thumbnails, each one an <a> to the full-size original. That is the entire lightbox.

  • Dark mode is color-scheme plus light-dark(), with no toggle to persist.

  • Navigation is a <ul> with flex-wrap. It reflows on a narrow screen because that is what flex-wrap does.

  • Layout shift has to be prevented rather than papered over, so every <img> carries its intrinsic width and height from the source file alongside its srcset.

The last one is the interesting inversion. Without JavaScript there’s nothing to smooth over a page that jumps while images load — so the discipline of emitting real dimensions matters more, not less.

It’s enforced by a test rather than by good intentions: after every build, the test suite asserts there is no <script, no on*= handler attribute, and no .js file anywhere in the output. Constraints that live only in your head erode.
